<objective>
Build the self-update path (DEPLOY-04). A self-update runs as a worker-owned
arq job (`run_self_update`) — the worker is a separate systemd unit so it
survives the API restart and can verify health + auto-rollback. The update
pulls a tagged semver release verified against a SHA-256 manifest (D-10, also
closes carryover ME-03), takes a WAL-safe pre-update DB snapshot (D-11),
performs an atomic symlink swap, and on failure auto-restores the DB and reverts
the code. Two triggers: an in-app admin button (route) and `install.sh --update`
/ re-running against an existing CTID (D-09/D-12).

This is the highest-risk plan in the phase. The sequence is RESEARCH §Pattern 5,
verbatim — do not improvise.

Purpose: DEPLOY-04 — an operator updates the GUI without manual file edits, and
re-running the helper-script is a real, idempotent update.

Output: the `run_self_update` job; the `/api/v1/admin/self-update` route;
`deploy/lxc/update.sh`; `install.sh --update` + existing-CTID handling; the
`releases/<tag>` + `current` symlink deploy layout.
</objective>

WAL-safe DB snapshot — RESEARCH §Code Examples (verbatim, Pitfall 1):
  import sqlite3
  def snapshot_db(src_path, dst_path):
      with sqlite3.connect(src_path) as src, sqlite3.connect(dst_path) as dst:
          src.backup(dst)

run_self_update sequence — RESEARCH §Pattern 5 (DO NOT improvise):
  1. fetch release manifest + tarball over HTTPS
  2. hashlib.sha256 the tarball, compare to manifest — abort on mismatch
  3. WAL-safe DB snapshot → app.db.pre-update
  4. unpack into releases/<tag>/; pip install -e backend; use COMMITTED frontend/build/
  5. alembic upgrade head
  6. atomic symlink swap: current -> releases/<tag>  (ln -sfn)
  7. systemctl restart proxmox-gui-api proxmox-gui-frontend  (API DIES HERE)
  8. poll new API GET /api/v1/health up to ~60s
  9. healthy -> mark job done, systemctl restart proxmox-gui-worker LAST
  10. unhealthy -> restore app.db, repoint symlink, restart api, mark job failed

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet → run_self_update (release tarball) | A pulled release payload is untrusted until verified |
| browser → /api/v1/admin/self-update | An admin-only trigger that restarts the whole service |
| PVE host → LXC (install.sh --update) | A privileged operator action that re-enters the LXC |
| update process → /opt vs /etc + /var/lib | The swap must touch only code, never persistent secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Tampering | self-update supply chain (tampered release tarball) | mitigate | `verify_sha256` checks the downloaded tarball against the published SHA-256 manifest BEFORE unpack; the job aborts on mismatch (D-10, closes ME-03). Updates pull only from tagged releases, never `master`. |
| T-05-04-02 | Denial of Service | a failed update bricking the install | mitigate | Auto-rollback (D-11) — a WAL-safe pre-update DB snapshot + symlink revert + API restart on a failed migration or health check. `install.sh --update` is the out-of-band recovery path when the UI itself is broken (D-09). |
| T-05-04-03 | Tampering / DoS | master key or GUI SSH private key clobbered by an update | mitigate | All persistent state lives under `/etc/proxmox-gui` + `/var/lib/proxmox-gui`; the symlink swap touches only `/opt/proxmox-gui`. The job asserts the swap target is `/opt/...` only (Pitfall 7). |
| T-05-04-04 | Data loss | WAL-mode DB snapshot taken with a plain file copy | mitigate | `snapshot_db` uses the stdlib `sqlite3` online-backup API (`.backup`) which folds in the `-wal` file; a `shutil.copy` is explicitly forbidden (Pitfall 1). |
| T-05-04-05 | Elevation of Privilege | the unprivileged worker calling systemctl | mitigate | A scoped sudoers entry permits `proxmox-gui` to `systemctl restart` exactly the three named units and nothing else (Open Question Q2 resolution) — narrowly scoped, documented. |
| T-05-04-06 | Tampering | install.sh --update re-appending the SSH pubkey unbounded | mitigate | The `authorized_keys` append is idempotent — `grep -qF "$PUBKEY" || echo >>` (Pitfall 6) — so a re-run does not grow the file with duplicates. |
| T-05-04-07 | Elevation of Privilege | /api/v1/admin/self-update triggered by a non-admin | mitigate | The route is `[Depends(require_admin), Depends(csrf_protect)]` — a non-admin gets 403, a forged cross-site request fails the CSRF check. |
| T-05-04-08 | Tampering | the API process trying to restart itself mid-update | mitigate | The orchestration runs in the worker (a separate systemd unit) — the API restart in step 5 kills the API but not the worker, so rollback can still run (Pitfall 2). |
| T-05-04-09 | Information Disclosure | release manifest fetched over a downgraded connection | accept | The manifest + tarball are fetched over HTTPS from GitHub Releases (TLS-validated against the public CA set); the SHA-256 manifest check is the integrity backstop even if transport were degraded. |
</threat_model>
