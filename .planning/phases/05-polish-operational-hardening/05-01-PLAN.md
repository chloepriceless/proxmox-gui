<objective>
Build the DB-backed runtime Settings layer (D-01) and the server-authoritative
idle-session-timeout backend (AUTH-06). Settings is the canonical home for the
idle-timeout value (D-02, default 30 min) and the audit-retention value (D-06,
default 1 year). The idle check is layered onto the existing refresh-token
rotation chokepoint.

This plan also lands the single Phase-5 Alembic migration `0007_phase5` (the
`settings` table + the `refresh_tokens.last_active_at` column) and registers
the three new arq job entry points in `worker.py` so downstream plans 05-03 and
05-04 do not need to re-edit `worker.py`.

Purpose: AUTH-06 — sessions expire after a configurable idle timeout, enforced
server-side so a tampered client clock cannot bypass it. D-01 — operators tune
runtime values without a restart.

Output: `settings` table + admin GET/PATCH endpoint; `last_active_at` on
`refresh_tokens`; idle-expiry refusal inside `consume_refresh`; a
`POST /api/v1/auth/keepalive` route; the `0007_phase5` migration; three arq
job/cron registrations in `WorkerSettings`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser cookie → /auth/refresh | An untrusted client presents a refresh-token cookie; the idle gate must be server-authoritative |
| browser → /api/v1/admin/settings | Admin-only mutation surface; a non-admin or forged request must be rejected |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01-01 | Elevation of Privilege | idle-timeout enforcement | mitigate | The idle check lives inside `consume_refresh` (the single server-side chokepoint). A client-side timer is UX-only — disabling JS or replaying the cookie still hits the server gate, which refuses the refresh once `now - last_active_at > idle_window`. |
| T-05-01-02 | Spoofing | /auth/keepalive | mitigate | Keepalive resolves the httpOnly refresh cookie and looks up a live, non-revoked row before bumping `last_active_at`; an invalid/missing cookie returns 401. It never issues a token, so it cannot be used to forge a session. |
| T-05-01-03 | Elevation of Privilege | /api/v1/admin/settings PATCH | mitigate | Route is `[Depends(require_admin), Depends(csrf_protect)]`. A non-admin gets 403; a cross-site forged request fails the CSRF double-submit check. |
| T-05-01-04 | Denial of Service | 0007 migration backfill | mitigate | The migration backfills `last_active_at = created_at` for every existing row (Pitfall 3) so a deploy does not instantly idle-expire every active session and trigger a re-auth flood. The idle check is also NULL-defensive as belt-and-braces. |
| T-05-01-05 | Repudiation | settings mutation | mitigate | `update_settings` writes an `audit_log` row (`settings.update`) with `payload_before`/`payload_after` and the actor user id — every runtime-config change is attributable. |
| T-05-01-06 | Tampering | session idle window value | accept | The idle window is admin-set runtime config; an admin lowering it is a legitimate operation. `Field(ge=1, le=1440)` bounds it to a sane range so it cannot be set to 0 (instant logout) or absurdly high. |
</threat_model>
