# Phase 1: Foundation - Context

**Gathered:** 2026-05-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Project scaffold + multi-tenant SQLite schema + local auth + per-cluster encrypted token storage + OpenAPI-backed REST shell + SvelteKit UI skeleton + first-run installer + admin/cluster setup wizard.

What this phase delivers (success-criteria-anchored):
1. One-line helper-script install reaches a first-run wizard that creates the initial admin user (cluster + SSH key optional).
2. Any user can log in (Argon2id), see a Hetzner-style shell with light/dark mode, change their own password, manage SSH keys, log out — session survives browser refresh.
3. Admin can create, edit, disable, delete users and assign them to teams.
4. Admin can register one or more Proxmox clusters (PVE 8.x+) with URL + per-cluster API token; tokens stored encrypted at rest; cluster context appears in every resource URL (`/api/v1/clusters/{id}/...`).
5. REST API exposes every shipped capability with auto-generated OpenAPI 3.1 + PAT auth working alongside session cookies. UI consumes the same API.

What this phase does NOT deliver:
- VM/LXC inventory, list, detail, RRD metrics (Phase 2)
- Quotas and audit log (Phase 2)
- Cluster switcher / reachability UX (Phase 2)
- Job queue / arq / UPID polling (Phase 3)
- Lifecycle actions (Phase 3)
- Provisioning wizards / SDN / noVNC (Phase 4)
- Idle session timeout (Phase 5)
- Mobile responsiveness audit (Phase 5)
- Self-update (Phase 5)

</domain>

<decisions>
## Implementation Decisions

### Tenant ↔ Proxmox Auth
- **D-01:** Per-tenant privilege-separated PVE tokens. Each app-tenant (team) maps to a PVE user + pool + privilege-separated API token. Proxmox enforces ACLs natively — directly mitigates Pitfall 5 (multi-tenant ACL leaks).
- **D-02:** Auto-bootstrap on tenant create. When admin creates a team in the GUI, backend immediately creates the matching PVE user, pool, and privilege-separated token on every registered cluster. Failure to bootstrap on any cluster blocks team creation (transactional across DB + PVE; rollback on partial failure).
- **D-03:** Cluster-registration token is Administrator-level. Admin pastes a high-privilege token (`User.Modify`, `Pool.Allocate`, `Realm.Allocate`, `Sys.Audit` at `/` — effectively Administrator role) when registering a cluster. GUI keeps it encrypted at rest and uses it for both tenant provisioning and runtime ops in v1.
- **D-04:** Tenant delete is blocked when the tenant owns any VMs/LXCs. Admin must migrate or delete resources first. No cascade-delete of PVE objects from the GUI. Tenant in "disabled" state blocks logins/API use but leaves PVE-side objects intact.

### Tenancy & Ownership Model
- **D-05:** Team is the primary tenant boundary. Every user has an auto-created **personal team** (immutable name/membership) plus may belong to N **shared teams**. Many-to-many user↔team relationship.
- **D-06:** One PVE pool per team. Personal teams get their own pool too. No per-user pools.
- **D-07:** Resource ownership is team-level. VMs/LXCs hang off `team_id`; every team member is an equal editor in v1. `created_by_user_id` is informational/audit metadata only (no elevated rights).
- **D-08:** **Quota math (deviates from standard "both must pass"):** Per-team quota applies when a user is in any shared team(s) — per-user quota is ignored in that case. Per-user quota is enforced ONLY when the user is solo in their personal team (i.e., not a member of any shared team). Admission control evaluates whichever side is active.

### GUI Auth Surface — Sessions
- **D-09:** Session credentials live in httpOnly + Secure + SameSite=Lax cookies. Both the access JWT and the refresh token. JS never touches them — pure cookie-attached transport.
- **D-10:** Access JWT TTL: 15 minutes. Refresh token TTL: 7 days. Refresh rotates on every use (old refresh invalidated, new one issued).
- **D-11:** Refresh tokens are DB-stored (Fernet-encrypted or hashed; see D-15) for server-side revocation. AUTH-07 "disable user" must invalidate live refresh tokens immediately.

### GUI Auth Surface — PATs (API-02)
- **D-12:** PATs use `Authorization: Bearer <token>` header — same surface as session JWT, distinguished by token prefix or table lookup. PAT inherits the user's tenants + role exactly (no per-PAT scope in v1). User-facing config: name + optional expiry. Revocation UI lives in a per-user Tokens settings page. Token value shown once at creation, not retrievable after.

### GUI Auth Surface — CSRF
- **D-13:** CSRF via double-submit cookie + SameSite=Lax. A CSRF token cookie is JS-readable; SvelteKit echoes it back via `X-CSRF-Token` header on state-changing requests for cookie-session calls. Bearer-PAT calls skip CSRF (no cookie to leak).

### Token-at-Rest Encryption
- **D-14:** Master key generated by helper-script installer. 32 bytes random, written to `/etc/proxmox-gui/master.key` (mode 0600, owned by the FastAPI service user) on first install. FastAPI reads it on boot. Master key is part of the GUI's persistent state and MUST be included in any self-backup flow (Pitfall 22).
- **D-15:** Symmetric crypto = **Fernet** (from the `cryptography` library). Used for: per-cluster PVE API tokens at rest, DB-stored refresh tokens, PAT-secret hashing pepper. Already a transitive dependency; battle-tested for this exact use case.

### First-Run Wizard + LXC Packaging
- **D-16:** LXC base OS: **Debian 12 (Bookworm)**. Matches Proxmox VE's own host OS, longest community-scripts familiarity. Python 3.12 installed via the official Debian Python team's backports or pyenv-built — concrete approach is Claude's discretion.
- **D-17:** Process supervision: three **systemd units** inside the LXC — `proxmox-gui-api.service` (FastAPI/uvicorn), `proxmox-gui-worker.service` (arq), `caddy.service`. LXC requires `nesting=1` (systemd-in-LXC). All unit logs go to journald.
- **D-18:** First-run wizard validation is **lenient**. Only the initial admin user is mandatory to finish. Cluster registration and SSH key are optional in the wizard and can be added post-install from the settings/cluster pages. Post-install, an in-app onboarding banner (or dashboard hint) surfaces "add a cluster" until at least one is registered.
- **D-19:** Wizard UX is a **multi-step stepper** (3–4 steps): Welcome → Create admin → Register first cluster (skippable) → Done. Back button works within the stepper; required fields in a step must be valid before advancing; the cluster step has a "Skip for now" link rather than a hard requirement.

### Claude's Discretion
- Unprivileged LXC feature set beyond `nesting=1` (likely add `keyctl=1`; `fuse` only if needed)
- Default LXC sizing for the helper-script (initial CPU / RAM / disk allocation)
- Caddy auto-HTTPS strategy (Let's Encrypt for public installs vs self-signed for LAN; both supported via Caddyfile)
- FastAPI service-user (non-root inside the LXC, e.g. `proxmox-gui`)
- Logging detail and level (journald default; structured JSON for the API service)
- DB migration tooling baseline (Alembic from revision 001 = initial schema; how to bootstrap on a fresh container)
- UI shell shape — Hetzner-Cloud-style sidebar nav with topbar cluster switcher (placeholder in Phase 1 — switcher activates in Phase 2). shadcn-svelte default theme tokens as the starting palette.
- Light/dark mode strategy — `class` strategy on `<html>`; system-preference detection + persisted user override
- SSH key storage shape — normalized entries (name, public_key, fingerprint, created_at) keyed to user_id
- User-disable semantics — soft flag (`is_active`); existing sessions/PATs revoked immediately; user's team memberships and quota usage preserved for re-enable
- OpenAPI doc serving paths — likely `/api/docs` (Swagger UI) and `/api/redoc` (ReDoc); `/api/openapi.json` for the spec
- Password complexity policy (minimum length + zxcvbn-style strength meter in the UI)
- Login rate-limiting / lockout policy (in-memory bucketed limiter for v1)
- PVE-side naming conventions: pool `gui-team-<id>`, user `gui-team-<id>@pve`, token `gui-team-<id>!api`
- Half-bootstrap cleanup: if PVE user creation succeeds but token creation fails on a cluster, the GUI rolls back the PVE user before failing the GUI tenant-create
- API endpoint versioning — `/api/v1/` is the only version in v1; the version segment is mandatory in every URL from day one

</decisions>

<specifics>
## Specific Ideas

- Hetzner Cloud design inspiration: stepper-style onboarding, clean cards, sidebar layout with topbar context switcher.
- shadcn-svelte default theme tokens are the starting palette — don't custom-design a theme in Phase 1; ship defaults.
- Multi-step stepper for first-run wizard is the preferred UX (chat-style and single-page-form options explicitly rejected).
- "Lenient" first-run validation deliberately chosen over "strict" — operator can boot the GUI and explore before committing PVE creds. Required: admin user. Optional in wizard: cluster registration, SSH key.
- Per-PAT scope deferred to v2 — keep v1 PATs inheriting full user perms to ship faster.
- Master key path: `/etc/proxmox-gui/master.key`, mode 0600.
- PVE-side naming convention (Claude's discretion): `gui-team-<id>` for pool / user / token names — predictable, namespaced, unlikely to collide with operator's own PVE entities.

</specifics>

<deferred>
## Deferred Ideas

- **Per-PAT scope** (read-only / read-write / per-team) — v2. v1 PATs inherit full user perms.
- **Team-role split** (creator-elevated-rights, viewer-vs-editor) — v2. v1 = everyone in a team is an equal editor.
- **Hybrid PVE auth** (super-token for writes + per-tenant token for reads) — not v1; revisit only if per-tenant operational cost is unacceptable.
- **Passphrase-wrapped master key** (the hybrid encryption-key option) — v1.x enhancement once core ships; default stays "random key in /etc".
- **Cascade-delete tenant + PVE objects** — explicitly rejected. Admin cleanup is manual.
- **Two-token PVE model** (bootstrap + scoped runtime token) — interesting future hardening; out of scope for v1.
- **2FA / WebAuthn / OIDC** — v2 per PROJECT.md.
- **Audit log writer** — Phase 2 (lives there per ROADMAP).
- **Idle session timeout** (AUTH-06) — Phase 5.
- **Cluster reachability indicator + read-only banner** (CLUST-03, CLUST-04) — Phase 2.
- **Cluster switcher dropdown** (CLUST-02) — Phase 2 (Phase 1 ships a placeholder; cluster context is in URLs from day one but the switcher UX lands in Phase 2).
- **Mobile responsiveness, helper-script polish, self-update** — Phase 5.

</deferred>
