## Schema-Invariant ALLOWLIST

Tables exempted from the "must have `team_id`" invariant, with rationale (documented inline in `test_schema_invariants.py`):

| Table | Rationale |
| --- | --- |
| `users` | Authentication identity; tenant lives in `teams`, not on the user row. |
| `teams` | A team IS the tenant; team_id on this table would be its own id. |
| `clusters` | Cluster is shared infra (multi-tenant per row via `team_cluster_tokens`), not tenant data itself. |
| `team_memberships` | The tenant FK lives in the composite PK `(team_id, user_id)`; the column IS `team_id`, but the invariant check looks for the column on non-PK columns, so it's allow-listed for completeness. |
| `audit_log` | Carries a NULLABLE `team_id` (Pitfall 5 — present from row 1, NULL for system events). Allow-listed for the NOT-NULL flavour of the check; a separate test asserts the column exists. |
| `ssh_keys` | User-scoped artefact; user_id is the natural owner. Team membership is irrelevant to SSH key ownership. |
| `personal_access_tokens` | User-scoped artefact (the "personal" in PAT). Same reasoning as ssh_keys. |
| `refresh_tokens` | Per-session credential bound to a user. Tenants don't share refresh tokens. |
| `alembic_version` | Alembic housekeeping, not application data. |

Adding a new entry to this allowlist requires editing the test AND writing a one-line rationale — this is the canonical record. Pitfall A5 mitigation.

## Decisions Made

- **EncryptedSecret renders as `sa.LargeBinary` in the migration** (not as the decorator class). Reason: the migration must be portable across changes to the decorator's docstring or type annotations. The ORM model is the only place the decorator type matters; SQLAlchemy stores the same `BLOB` either way.
- **Personal team name format = `personal-<user_id>`** (per 01-RESEARCH.md §Anti-Patterns), not `<username>-personal`. Decision documented in `app/models/team.py` docstring; format enforcement happens at write time in Plan 07's `create_user`.
- **Migration is hand-written, not autogenerated.** Trade-off: more verbose, but every constraint has a stable name (`fk_*`, `uq_*`, `ck_*`, `ix_*`) which is important under batch mode (anonymous constraints break round-trip downgrade in SQLite).
- **Downgrade order is dependency-reverse** so `PRAGMA foreign_keys = ON` (set by `app/core/db.py`'s PRAGMA listener) does not raise on drops.
- **`prepend_sys_path = .` in alembic.ini** — without this, the installer-time `alembic upgrade head` CLI invocation fails with `ModuleNotFoundError: No module named 'app'`. Pytest already provided this via `pyproject.toml::pythonpath`, but the CLI doesn't read pyproject.

- **Files modified:** `backend/tests/test_models_metadata.py`

**2. [Rule 3 - Blocking] em-dash in alembic.ini broke configparser under broken locale**

- **Found during:** Task 2 GREEN, first attempt to run migration tests.
- **Issue:** The shell warns `setlocale: LC_ALL: cannot change locale (de_DE.UTF-8)` on every command (system locale is mis-configured). `configparser.read(..., encoding="locale")` falls back to ASCII; my `alembic.ini` contained em-dashes in comments → `UnicodeDecodeError: 'ascii' codec can't decode byte 0xe2`.
- **Fix:** Replaced every em-dash with `--` in `alembic.ini`. The file is now pure ASCII and works regardless of locale — defensive against any future deployment environment with a broken locale (servers without UTF-8 locales are common).
- **Files modified:** `backend/alembic.ini`
- **Committed in:** `ee56b0e` (same commit as the GREEN migration).

**3. [Rule 3 - Blocking] `revision = "0001_initial"` test regex was too strict**

- **Found during:** Task 2 GREEN, regex test against migration content.
- **Issue:** The acceptance-criteria test used a literal substring match for `'revision = "0001_initial"'`. My migration uses the PEP 526 annotated form `revision: str = "0001_initial"`, which is the standard modern Alembic template style.
- **Fix:** Replaced the literal match with a regex (`^\s*revision(?:\s*:\s*[^=]+)?\s*=\s*["\']0001_initial["\']`) that accepts both annotated and unannotated forms. Spirit of the plan acceptance criterion (`grep -q '0001_initial'`) is preserved.
- **Files modified:** `backend/tests/test_migrations.py`
- **Committed in:** `ee56b0e`.

**4. [Rule 3 - Blocking] alembic CLI from `backend/` failed with `ModuleNotFoundError`**

Pytest worked because `pyproject.toml::[tool.pytest.ini_options].pythonpath = ["."]` sets it. The installer (Plan 04) will run `alembic upgrade head` from the CLI, so this had to work.
- **Fix:** Added `prepend_sys_path = .` to `[alembic]` in `alembic.ini`. Now CLI and pytest behave identically.

## Issues Encountered

- **System locale is broken** (`setlocale: LC_ALL: cannot change locale (de_DE.UTF-8)`). Worked around by keeping `alembic.ini` ASCII-only. Source files (Python) are explicit UTF-8 via PEP 263 default; only `configparser`-parsed files needed the workaround.
- **`alembic -x url=... upgrade head` does not override the URL** by itself — env.py would have to explicitly read `context.get_x_argument()`. The CLI used the `sqlalchemy.url` in `alembic.ini` instead. Not a blocker because the app loads the runtime URL via `app/core/db.py::run_migrations` which sets `cfg.main_option("sqlalchemy.url", ...)`; the CLI placeholder URL is only used during manual operator inspection.
