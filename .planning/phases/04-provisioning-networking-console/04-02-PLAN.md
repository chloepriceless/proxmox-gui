<objective>
De-risk SDN networking — research-flagged MEDIUM-LOW confidence and ROADMAP-mandated spike 1. SDN has a two-state model (pending vs applied), no documented next-free-IP REST endpoint, and version-sensitive behavior.

Purpose: Phase 4 READS SDN (the GUI consumes admin-defined SDN — it never provisions zones, per CONTEXT). But the read path is unclear: how does the API expose applied-vs-pending state (Pitfall 8)? Is there a free-IP endpoint for IPAM (Pitfall 5, NET-03)? This spike resolves it before 04-07 implements `networks/service.py`.

Output: `04-SPIKE-sdn.md` — findings with the confirmed read-API contract, the IPAM mechanism (or the DHCP-only degrade decision), the version floor, and how legacy bridges are enumerated. No production code ships here.
</objective>

Investigate the Proxmox SDN API and produce a findings document at `.planning/phases/04-provisioning-networking-console/04-SPIKE-sdn.md`. Use WebFetch against `https://pve.proxmox.com/wiki/Software-Defined_Network` and `https://pve.proxmox.com/pve-docs/api-viewer/` (the API viewer) to inspect the SDN endpoint tree. The document MUST answer these specific questions, each as its own `##` section with a verdict line and evidence:

1. **Zone / VNet / subnet read endpoints.** Document the exact API paths for enumerating SDN zones (`GET /cluster/sdn/zones`), VNets (`GET /cluster/sdn/vnets`), and subnets, including their query parameters. Document the response field set for each — for a VNet, which fields identify its zone, its tag, and (critically) any IPAM association. Verdict line: `VNET READ: <path> — IPAM field: <field name or "none">`.

2. **Applied-vs-pending state (Pitfall 8, the gating question for NET-01).** Determine how the API distinguishes an SDN object that is configured (`/etc/pve/sdn/`) from one that is applied (`/etc/network/interfaces.d/`). Check whether the zones/vnets endpoints carry a `state`, `pending`, or `running` indicator, OR whether the GUI must read `/cluster/sdn` status, the `.running-config`/`.version` files, or the `pending=1` query parameter. Document exactly how `networks/service.py` will tell a usable applied VNet from a not-yet-applied one. Verdict line: `APPLIED STATE READ: <mechanism>`.

3. **IPAM next-free-IP mechanism (Pitfall 5, A3 — gates NET-03).** Determine whether a reliable "next free IP for subnet X" path exists. Evaluate the three options from RESEARCH Open Question 2: (a) `POST /cluster/sdn/vnets/{vnet}/ips` to allocate-and-read-back; (b) read the subnet's IPAM range + the VNet's currently-allocated IPs and compute the next free one app-side; (c) DHCP-only degrade. Document which option is viable, with the exact endpoint(s). If none gives a clean free-IP, the verdict is the DHCP-only degrade (D-20 already permits the user to switch to DHCP). Verdict line: `IPAM FREE-IP: <option a|b|c> — endpoint(s): <paths or "n/a — DHCP-only degrade">`.

4. **Version floor + SDN-capable detection (D-21).** Document the minimum PVE version SDN is reliably usable on (research says 8.0-8.1; IPAM partly preview). Document how the GUI detects, per cluster, whether SDN is configured and usable — e.g. the connector already has a cluster version probe; document whether "SDN configured" means "the `/cluster/sdn/zones` endpoint returns at least one zone" or a separate capability check. Verdict line: `SDN VERSION FLOOR: PVE <x.y> — detection: <mechanism>`.

5. **Legacy-bridge enumeration (NET-04, D-19).** Document the API path to list legacy Linux bridges on a node/cluster (likely `GET /nodes/{node}/network` filtered to `type=bridge`). This is the fallback path and the default-visible network type. Verdict line: `LEGACY BRIDGE READ: <path>`.

6. **Partial-node-offline behavior.** Document what the SDN read endpoints return when one cluster node is out of quorum or offline (Pitfall 8 says SDN apply is cluster-wide). State whether the GUI's reads degrade gracefully or error, and what `networks/service.py` should do (mirror the Phase-2 stale-cache graceful-degradation pattern).

7. **Read-API contract for 04-07.** A summary section: the concrete list of connector read methods 04-07 must add (`sdn_zones`, `sdn_vnets`, `sdn_subnets`, `node_bridges`, and an IPAM method or none), each with its exact PVE path, and the shape of the flat picker list `networks/service.py` will return to the frontend (a list grouped into "SDN VNets" vs "Legacy bridges", each entry carrying applied-state and IPAM-availability flags per the UI-SPEC §SDN-aware network picker).

Reference D-18, D-19, D-20, D-21 by ID. Every claim must be backed by a quoted API-viewer path/field or a wiki citation — not assumed. Where the live cluster check is unavailable, mark the claim `[ASSUMED — verify at implementation]` and state the degrade.
