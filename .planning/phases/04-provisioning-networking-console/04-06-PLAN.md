<objective>
Build the community-scripts catalog backend (curated shortlist + searchable full catalog with source/commit/last-reviewed visibility) and the two-stage `run_community_script` job. This is the spike-gated half of LXC provisioning that 04-04 deliberately deferred.

Purpose: LXC-01/02 need a browsable catalog (curated + full-search) sourced from a bundled floor snapshot with admin sync (D-05/D-06). LXC-04 needs source/commit-hash/last-reviewed-date surfaced before deploy. LXC-03 needs the one-click non-interactive deploy — the two-stage job: the GUI creates the empty LXC itself (Pitfall 10), then runs ONLY the upstream install stage inside it via `pct exec`/`lxc_exec`, streaming output to the Tasks drawer (D-08). The exact `lxc_exec` mechanism and the stage-2 install contract are pinned by spike 04-01 (`04-SPIKE-community-scripts.md`).

Output: `GET /api/v1/clusters/{id}/catalog` (curated + full + search), `POST /api/v1/catalog/sync` (admin re-pin), the vendored `snapshot.json` floor, and the `run_community_script` job function the wizard's Community-Script path enqueues.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| upstream community-scripts repo → GUI | Untrusted third-party bash; pinned to a reviewed commit, never "latest" |
| GUI → freshly-created LXC (`lxc_exec`) | The install stage runs as root INSIDE the new container — never on the PVE host |
| browser/PAT client → community-script create API | User-controlled `script_slug`, `script_options`, sizing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06-01 | Elevation | `pct exec` command injection via script slug / options | mitigate | `script_slug` is validated against the catalog entry set (only a known slug resolves to a script); `script_options` values flow as discrete env-var / argument values to `lxc_exec`'s `command` list (a list, never a shell string — no shell interpolation); the install stage runs INSIDE the fresh LXC via `lxc_exec`, never on the host (Pitfall 10) |
| T-04-06-02 | Tampering | Catalog commit-pin tampering / "always latest" | mitigate | The vendored `snapshot.json` floor pins a 40-char reviewed SHA; `sync_catalog` re-pins to a deliberately-resolved commit and records `synced_by_user_id`; the install script is always fetched at the pinned SHA — never the moving default branch |
| T-04-06-03 | Elevation | Catalog sync open to non-admins | mitigate | `POST /catalog/sync` carries `Depends(require_admin)` + `Depends(csrf_protect)`; a non-admin → 403; re-pinning the supply-chain floor is an admin-only act |
| T-04-06-04 | Information disclosure | Cross-tenant community-script create | mitigate | The create route resolves the principal's team; a create for a team the principal does not belong to → 403; the LXC is created as the per-team privsep token and joins the team pool (`pool=` in `to_pve_config`) |
| T-04-06-05 | Tampering | Orphan LXC on stage-2 install failure | accept | A stage-2 failure marks the job failed but deliberately keeps the created LXC (Pitfall 8) — the user owns a created-but-install-failed container they can inspect or delete via the Phase-3 lifecycle UI; auto-delete would destroy user data |
</threat_model>
