<objective>
Build the Phase-4 frontend foundation: the five typed API client modules, the two shared primitives (`EmptyState`, `HelpTooltip`), the `/create` wizard route shell with its chrome + Step 1 path picker, and the sessionStorage draft store. This plan owns the shared/foundational frontend files so the three sibling frontend plans (04-10/11/12) can build their own wizard steps without conflict.

Purpose: Every Phase-4 frontend surface needs typed API clients (04-PATTERNS.md — `lifecycle.ts` is the exact analog). UI-04 needs a reusable `EmptyState`; UI-05 needs a reusable `HelpTooltip`. The wizard chrome (header, stepper rail, footer, Step-1 path picker, step orchestration, draft persistence) is the skeleton every wizard-step plan plugs into. Building it once here prevents the wizard `+page.svelte` becoming a four-plan merge conflict.

Output: `api/{provisioning,catalog,networks,iso,console}.ts`, `EmptyState.svelte`, `HelpTooltip.svelte`, `routes/create/+page.svelte` (+ `+page.server.ts`), `WizardChrome.svelte`, `PathPicker.svelte`, the `wizardDraft` store, and the `/inventory` "Create" button + empty state.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /create SSR loader | The wizard route is auth-gated; an unauthenticated user is redirected to login |
| browser sessionStorage ↔ wizard draft | Wizard draft is client-only state — no secrets are persisted to sessionStorage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-09-01 | Spoofing | Unauthenticated wizard access | mitigate | `create/+page.server.ts` is an auth-gated SSR loader (the `admin/teams/[id]` analog) — an unauthenticated user is redirected to login before the wizard renders; the real authorization is enforced server-side on the create POST (Plan 04-04) |
| T-04-09-02 | Information disclosure | Secrets persisted to sessionStorage | mitigate | The `wizardDraft` store persists only non-secret wizard form state (path, sizing, selected names) — no passwords, no tokens; `cipassword` (Cloud-Init) is handled by the 04-12 editor and is NOT written to the draft store |
| T-04-09-03 | Tampering | Stale/forged wizard draft replayed | accept | A tampered `sessionStorage` draft only pre-fills wizard fields the user can see and edit; every value is re-validated client-side and re-authorized server-side on submit — a forged draft cannot bypass quota admission or tenancy checks |
</threat_model>
