`backend/app/clusters/connector.py:893`:
```python
async def node_resources(self) -> list[dict]:
    """GET /cluster/resources?type=node — per-node CPU/RAM capacity.
    Returns the type=node rows, each carrying maxcpu/cpu/maxmem/mem ...
    """
```
Each returned dict carries (Proxmox `/cluster/resources?type=node` row shape):
- `node` — the node name (string)
- `maxcpu` — total CPU cores on the node (integer)
- `cpu` — current CPU load as a **0-1 fraction** (float; e.g. 0.25 = 25% used)
- `maxmem` — total RAM in **bytes** (integer)
- `mem` — used RAM in **bytes** (integer)
- `status` — `online` / `offline`

UNIT MATH the route must perform:
- free CPU cores = `maxcpu - (cpu * maxcpu)` = `maxcpu * (1 - cpu)`  → a float, the node-fit
  consumer compares against integer requested cores; expose it as a float (NodeResource.freeCpu)
- free RAM MB = `(maxmem - mem) / (1024 * 1024)`  → bytes → MB, integer-rounded (floor)

The connector is obtained per cluster. Existing cluster-scoped reads use the registry:
`backend/app/clusters/routes.py` has a `get_registry` dependency; the registry exposes
`registry.get(cluster_id, db=db)` (cluster-admin connector) and `registry.get_for_team(...)`.
`connector.node_resources()` reads `/cluster/resources` which the cluster-admin connector
can always enumerate — use `registry.get(cluster_id, db=db)`, mirroring the
`list_backup_storages` service function pattern (`backend/app/clusters/service.py`).

`node-fit.ts` consumes (frontend):
```typescript
interface NodeResource {
  node: string;
  freeCpu: number | null;     // free CPU cores
  freeRamMb: number | null;   // free RAM in MB
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `GET /clusters/{id}/nodes/resources` | An authenticated user requests per-node capacity figures for a cluster |
| route → PVE `/cluster/resources` | The cluster-admin connector reads cluster-wide node capacity |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-16-01 | Information disclosure | `GET /clusters/{id}/nodes/resources` | mitigate | The route requires an authenticated principal (`get_current_principal`); per-node capacity is cluster-wide infrastructure data (node names + free CPU/RAM) — not tenant-scoped resource data — and is needed by any user running the create wizard for that cluster; this matches the existing `list_backup_storages` cluster-read posture. No vncticket, no token, no per-VM data is exposed |
| T-04-16-02 | Denial of service | the PVE `/cluster/resources` read | accept | The read routes through `connector.node_resources()` → `_call_with_breaker` — the existing per-cluster circuit breaker bounds repeated failing calls; a breaker-open failure surfaces as a rejected promise the wizard catches (graceful degradation) rather than a hang |
| T-04-16-03 | Tampering | `cluster_id` path param | mitigate | `cluster_id` is an integer path param; the registry resolves it to a registered cluster row or raises — an unknown cluster id yields a 4xx, not a connection to an arbitrary host |
</threat_model>
