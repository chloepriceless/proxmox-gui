The console WebSocket reuses this exact auth-before-accept pattern (the ONLY in-repo analog for console/proxy.py):

```python
async def _resolve_ws_user(websocket, db) -> User | None:
    token = websocket.cookies.get("access_token")
    if not token:
        return None
    try:
        payload = decode_access_token(token)
        user_id = int(payload["sub"])
    except Exception:
        return None
    user = await db.get(User, user_id)
    return user if (user and user.is_active) else None
# ... authenticate BEFORE websocket.accept(); close(1008) on failure; cookie-only, no PAT.
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser iframe → GUI WS relay | Untrusted browser; the relay authenticates before `accept()` and never exposes the Proxmox host |
| GUI WS relay → Proxmox `wss://...:8006` | The only leg that holds the vncticket; the ticket never reaches the browser as a Proxmox-host URL |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-04-03-01 | Information disclosure | vncticket / Proxmox host exposure | mitigate | Spike confirms CON-03: the GUI reverse-proxies the WS — the Proxmox host:8006 URL and the vncticket are never handed to the browser; the ticket lives only on the relay's upstream leg |
| T-04-03-02 | Spoofing | Console WS handshake | mitigate | Spike pins the `jobs/ws.py` auth-before-accept pattern: authenticate the `access_token` cookie BEFORE `accept()`, cookie-only (no PAT), `close(1008)` on failure — 04-08 implements it |
