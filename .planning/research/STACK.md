# Stack Research

**Domain:** Self-hosted Proxmox VE/LXC self-service portal (Hetzner-Cloud-style), packaged as a single LXC.
**Researched:** 2026-05-14
**Confidence:** HIGH (core stack), MEDIUM (Proxmox-specific edge cases — SDN, cloud-init custom, noVNC embed)

## Decision Summary

**The single-LXC-friendly 2026 stack:**

- **Backend:** Python 3.12 + FastAPI 0.136.x (best ecosystem fit, **proxmoxer** is the only mature, actively-maintained, full-coverage Proxmox client in any language).
- **Proxmox client:** `proxmoxer` 2.3.x (active, 5.0.0/Stable, releases as recent as 2026-03-04).
- **Database:** SQLite (via SQLAlchemy 2.0 + `aiosqlite`) in WAL mode. No Postgres. No Redis-as-primary.
- **Frontend:** SvelteKit 2 + `adapter-node` served from the same LXC, Tailwind v4 + `shadcn-svelte` for the Hetzner-style aesthetic.
- **API protocol:** REST (OpenAPI 3.1, auto-generated by FastAPI).
- **WebSocket:** FastAPI's native WebSocket + an in-process pub/sub (`broadcaster` library) — no external Redis required for the single-LXC topology.
- **Background jobs:** `arq` 0.26.x + an embedded Redis (`redis` package) bundled inside the LXC. Reason in the queue section below — `BackgroundTasks` is not durable enough for Proxmox UPID polling.
- **Auth:** Local users with `pwdlib[argon2]` for hashing + PyJWT for short-lived access tokens + server-side refresh tokens persisted to SQLite (revocable).
- **noVNC:** Iframe-embed the Proxmox-hosted noVNC viewer using a per-VM, short-lived PVE ticket. **Do not** rebuild the viewer.
- **Cloud-Init:** Generate user-data/network-data with PyYAML + a small `cloud-init` schema validator (`cloud-init schema` shell-out is optional), upload to a Proxmox snippets storage, then set `cicustom` via proxmoxer.
- **SDN:** No dedicated SDN library exists. Talk raw to `/cluster/sdn/zones`, `/cluster/sdn/vnets`, `/cluster/sdn/vnets/{vnet}/subnets` through proxmoxer. Document this honestly.
- **Reverse proxy (inside the LXC):** Caddy 2 (single binary, automatic HTTPS, ~30 MB RAM). Fronts both the FastAPI and SvelteKit upstreams on one port.
- **Process supervision:** `s6-overlay` or plain `systemd` units (the LXC will have systemd available). Avoid Docker/Compose inside the LXC.

The justification for each choice is below.

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|---|---|---|
| Python + FastAPI | **Go + go-proxmox (luthermonson)** | Pick Go if you want a single static binary and don't need cloud-init helpers. Trade-off: `go-proxmox` 0.5.0 still lists cloud-init as a "wanted" feature, not implemented — you'd build it yourself. Picking Python is the lower-risk path. |
| Python + FastAPI | **Node.js + proxmox-api (UrielCh)** | Tempting because the frontend is Svelte (one language). Reject because: (a) last release 2024-09 = stale by 2026 standards, (b) ~80 stars = small bus factor, (c) FastAPI's OpenAPI generation is a force multiplier the Node ecosystem doesn't match. |
| SQLite | **PostgreSQL** | Only if you'll ever run >1 GUI instance for HA. For the "single LXC" constraint, Postgres adds a separate service to supervise and a real backup story; SQLite + Litestream covers 99% of homelab needs. |
| SQLite | **DuckDB / embedded KV (BoltDB)** | DuckDB is analytical; wrong workload. KV stores don't give you Alembic-style migrations — bad fit for evolving multi-tenant schema. |
| arq + Redis | **FastAPI BackgroundTasks** | Use for fire-and-forget audit-log writes ONLY. Not for Proxmox task polling — if the worker dies mid-UPID-watch, you lose the task state. |
| arq + Redis | **Celery** | Celery still has no native async/await in 2026 (issue open since 2020). FastAPI is async-native — bridging is painful. arq is the async-native Celery. |
| arq + Redis | **Dramatiq** | Good library, but its async support is bolted on. arq is async-first. |
| SQLAlchemy 2.0 async | **SQLModel** | SQLModel is a thin wrapper *by the FastAPI author* over SQLAlchemy + Pydantic. Fine choice, but lags SQLAlchemy releases by months and adds an abstraction we don't need (we already use Pydantic separately for request validation). Pick SQLModel only if you want one model class to serve both DB and API DTOs and accept the version lag. |
| SQLAlchemy 2.0 async | **Tortoise ORM** | Slower than async SQLAlchemy in benchmarks, smaller ecosystem, no Alembic — you'd use Aerich. Reject for SQL-heavy multi-tenant workloads. |
| SvelteKit | **Next.js 16 + React 19** | Pick if your team already lives in React. Trade-off: ~2× bundle size, more memory in the LXC, RSC complexity isn't useful for an internal admin tool. |
| SvelteKit | **Nuxt 4** | Excellent framework, but no concrete advantage over SvelteKit here and a slightly larger runtime. |
| SvelteKit | **HTMX + plain Jinja2 server-rendered FastAPI** | Tempting for "single language" — but the noVNC iframe, the live task progress, and the Cloud-Init editor (Monaco) all want real client-side state. HTMX hits a wall the first time a wizard needs reactive form state. |
| Caddy | **Nginx** | Use if your LXC base image already has Nginx pinned by org policy. Trade-off: manual cert-bot wiring vs Caddy's zero-config HTTPS. |
| Caddy | **Traefik** | Traefik is for service discovery (Docker labels, K8s ingresses). Overkill inside one LXC. |
| pwdlib | **bcrypt directly** | bcrypt is fine but the OWASP-2024+ recommendation is Argon2id. pwdlib gives you Argon2id with a clean upgrade story. |
| PyJWT | **python-jose** | python-jose is unmaintained (no release since 2023). |
| iframe-embed noVNC | **Roll our own noVNC viewer + proxy the WebSocket** | More control over UX but: (a) Proxmox PVE *modifies* upstream noVNC — you'd diverge, (b) it's a multi-week project, (c) the iframe path is what every commercial Proxmox-frontend (e.g., proxmox-vnc) does. Defer to v2 if needed. |

## What NOT to Use

| Avoid | Why | Use Instead |
|---|---|---|
| **`passlib`** | Last release 2020. Broken on Python 3.13+ (`crypt` module removal). Maintainer publicly considering EOL. | `pwdlib[argon2]` |
| **`python-jose`** | No releases since 2023. Security-sensitive code that nobody is patching. Known to ship vulnerable defaults for some algorithms. | `PyJWT` 2.10+ |
| **Celery** | No async/await in 2026 (the GitHub issue from 2020 is still open). Multi-process model is wrong for our single-LXC, I/O-bound, async-FastAPI workload. | `arq` |
| **Telmate/proxmox-api-go** | Effectively superseded by `luthermonson/go-proxmox`; if you go Go, use luthermonson. | `luthermonson/go-proxmox` (if Go) |
| **proxmox-api (npm) / node-proxmox / pvea** | Either unmaintained, low API coverage, or low bus factor (≤100 stars). FastAPI is the supported path. | `proxmoxer` |
| **Building your own noVNC** | PVE patches upstream noVNC; you'd inherit a maintenance treadmill. The iframe-embed path is documented and well-trodden. | Iframe the Proxmox-hosted noVNC with a short-lived PVEAuthCookie. |
| **PostgreSQL in v1** | A second service to install, supervise, back up, and migrate. Violates the "single LXC, drop-in" constraint. | SQLite + WAL + nightly `.backup` to a snippet dir or rclone. |
| **Docker / docker-compose inside the LXC** | Nested containerization on Proxmox is fragile (especially with unprivileged LXC + cgroupv2 + Docker's iptables expectations). The whole project's deployment story is "the LXC IS the container." | systemd units (or s6-overlay for unprivileged LXC). |
| **`requests` (sync) on the hot path** | proxmoxer is sync by default; calling it directly from a FastAPI `async def` blocks the event loop and kills WebSocket fanout. | Wrap proxmoxer calls in `await asyncio.to_thread(...)` or use a thread pool. |
| **Storing PVE ticket as the only auth state** | Tickets expire every 2 hours and need CSRF tokens for writes — your GUI will randomly 401 long-running operations. | Use **PVE API tokens** for backend-to-Proxmox auth. Use short-lived tickets ONLY when minting per-VM noVNC URLs (because noVNC needs a ticket, not a token). |
| **JWT for refresh tokens** | Stateless JWTs can't be revoked — a leaked refresh token is valid until expiry. | Store refresh tokens in SQLite, rotate on use, single-use; access tokens stay JWT. |
| **Hard-failing on cluster unreachability** | The PROJECT.md "Resilience" constraint says: degrade to read-only. A naked HTTP exception bubbling out of proxmoxer breaks the whole UI. | Wrap every proxmoxer call in a circuit-breaker (e.g., `purgatory` or hand-rolled) and surface a "cluster unreachable" banner. |

## Stack Patterns by Variant

**If the user goes single-LXC, single-cluster (90% of homelab installs):**
- Use the stack as-is.
- Run a single uvicorn worker — Proxmox is the bottleneck, not Python.
- In-memory `broadcaster` for WebSocket fanout is fine; Redis is only used by arq.

**If the user later scales to multiple GUI instances (HA):**
- Swap SQLite → PostgreSQL (one Alembic migration).
- Swap in-memory `broadcaster` → Redis-backed `broadcaster` (one config flip — both backends share the same API).
- Promote the embedded Redis to a separate LXC.
- Add a Caddy load balancer in front.
- The Python/JS code does NOT change. This is the payoff for picking abstractions (`broadcaster`, SQLAlchemy) that have multi-backend support from day one.

**If the user has very large clusters (>100 nodes per Proxmox cluster):**
- The proxmoxer call patterns (especially `/cluster/resources`) get expensive. Add a cache layer (`aiocache` or just a TTL'd dict).
- Move task-status polling out of the request path entirely — arq workers poll UPIDs, push results via WebSocket.

**If admin wants to disable the embedded Redis entirely (unusual but asked-for in some homelab forums):**
- Replace `arq` with `sqlite-queue` (very limited) or `apscheduler` with a SQLite job store.
- Trade-off: at-most-once delivery semantics; not recommended.

## Proxmox-Specific Gotchas (Critical for the Roadmap)

These shape the architecture; the roadmap will flag features that hit them.

1. **Auth: tickets vs. tokens.** Tickets are 2-hour-lived, require a CSRF prevention header on writes, and are tied to a user. API tokens are stateless, no CSRF needed, scoped permissions, revocable. **Use tokens for backend→Proxmox auth. Use tickets only when minting a noVNC URL** (since the embedded viewer needs a cookie). Generate the ticket on demand server-side, hand the cookie to the user's browser, embed the iframe — never expose the long-lived API token to the user's browser.

2. **UPID async tasks.** All long-running Proxmox operations (VM clone, migration, backup) return a UPID (`UPID:node:pid:pstart:starttime:type:id:user`). The API call returns the UPID immediately; you poll `/nodes/{node}/tasks/{upid}/status`. The GUI MUST treat every mutating call as async — show a progress card, poll in a background worker (arq job), push updates to the dashboard via WebSocket. **Do not** block the HTTP request until the UPID finishes. The user's wizard must return in <500ms with "Provisioning…" UI, not wait 90s for the clone.

3. **Cloud-Init `cicustom` requires a snippets-enabled storage.** Only storages with `content: snippets` enabled accept the custom user-data files. The GUI must enumerate eligible storages and either (a) refuse to do custom Cloud-Init if none exist, or (b) prompt the admin to enable one. Generated snippet path format: `local:snippets/vm-100-user.yaml`. Reference via `cicustom=user=local:snippets/vm-100-user.yaml`.

4. **SDN endpoints are NOT well covered by any client library.** proxmoxer's dynamic-attribute approach means you CAN reach them (`prox.cluster.sdn.zones.get()`) but there are no type hints, no helpers, and the SDN apply workflow (`/cluster/sdn` POST to apply pending changes — yes, SDN has a pending state) is undocumented in the Python ecosystem. Plan to write a thin internal `SdnClient` wrapper.

5. **Multi-cluster fan-out.** proxmoxer instances are per-cluster. The GUI's `ClusterPool` must maintain N proxmoxer instances, route requests by `cluster_id`, and handle the "this cluster is unreachable" case independently from healthy clusters — partial degradation, not all-or-nothing.

6. **Community-scripts integration.** The catalog is a GitHub repo (`community-scripts/ProxmoxVE`) with shell scripts and a metadata JSON sidecar. Fetch with a GitHub-API client (or a cached static snapshot bundled at build time). Run scripts via `pct exec` (proxmoxer's `nodes(node).lxc(vmid).status.exec.post(...)`) or by SSH-ing into the PVE node. **Do not** run them client-side — they need root on the PVE host.
